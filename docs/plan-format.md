# Формат плана

План передаётся в систему **только** через инструмент `submit_plan` ([mcp-tools.md](mcp-tools.md#submit_plan)). Система валидирует его, хранит в БД (`plans.content`), синхронизирует таблицу `tasks` и генерирует `docs/PLAN.md`.

## Структура

```json
{
  "summary": "Telegram-бот для учёта расходов: FastAPI + aiogram + PostgreSQL",
  "change_summary": null,
  "estimate_comment": "10 дней: 2 на каркас и БД, 5 на функции, 2 на отчёты, 1 запас",
  "test_command": "uv run pytest -q",
  "milestones": [
    {"key": "M1", "title": "Базовый бот", "version": "v0.1.0"},
    {"key": "M2", "title": "Отчёты", "version": "v0.2.0"}
  ],
  "days": [
    {
      "day": 1,
      "goal": "Каркас проекта и CI-скрипты",
      "tasks": [
        {
          "key": "T1",
          "title": "Каркас проекта",
          "description": "uv-проект, структура пакетов, конфиг через pydantic-settings, pytest",
          "acceptance_criteria": [
            "uv run pytest проходит",
            "есть README с запуском"
          ],
          "depends_on": [],
          "milestone": "M1"
        }
      ]
    }
  ]
}
```

| Поле | Обязательно | Описание |
|---|:-:|---|
| `summary` | ✓ | 1–3 предложения: что строим и на чём |
| `change_summary` | при перепланировании | Что изменилось и почему |
| `estimate_comment` | ✓ | Обоснование числа дней, риски. Если в заданное число дней проект не укладывается — здесь объяснение |
| `test_command` | ✓ | Команда, которую шлюз запускает перед мержем; код возврата 0 = успех |
| `milestones[]` | ✓ (≥1) | `key` (`M\d+`), `title`, `version` (semver с `v`) |
| `days[]` | ✓ | Дни по порядку |
| `days[].day` | ✓ | Номер дня |
| `days[].goal` | ✓ | Цель дня одной фразой |
| `days[].tasks[]` | ✓ (≥1) | Задачи в порядке выполнения |
| `tasks[].key` | ✓ | `T\d+`, уникален в проекте навсегда |
| `tasks[].title` | ✓ | ≤ 100 символов |
| `tasks[].description` | ✓ | Что сделать, достаточно для исполнителя без доступа к истории переписки |
| `tasks[].acceptance_criteria` | ✓ (≥1) | Проверяемые критерии |
| `tasks[].depends_on` | | Ключи задач |
| `tasks[].milestone` | ✓ | Ключ вехи |

## Валидация

Ошибки возвращаются агенту в ответе `submit_plan` списком (`путь: сообщение`), чтобы он исправил и отправил снова.

1. JSON соответствует схеме (pydantic-модель `PlanContent`).
2. Дни идут подряд без пропусков (см. перепланирование — с какого номера).
3. Ключи задач и вех уникальны; формат ключей.
4. `depends_on` ссылается на существующие задачи, и зависимость не позже самой задачи (тот же день и выше по порядку или раньше). Циклов нет.
5. `milestone` ссылается на существующую веху; у каждой вехи есть хотя бы одна задача.
6. Последняя веха включает последнюю задачу плана — к концу проекта всё выпущено в `main`.
7. Число дней — **не** ошибка: если оно отличается от `planned_days`, план принимается, а пользователь при согласовании видит предупреждение «агент предлагает N дней вместо M». Утверждение плана меняет `planned_days`.

## Перепланирование

План при перепланировании — **полный оставшийся план**, а не патч.

- Выполненные (`done`) задачи в план не входят и не меняются; их ключи нельзя переиспользовать.
- Задача в работе (`running`, `verifying`, `paused`) не может быть удалена; можно поменять её описание — исполнитель увидит новое при следующей сессии.
- Нумерация дней: начатый день (`current_day`, если в нём остались невыполненные задачи) сохраняет номер; новые дни нумеруются от `current_day + 1`. Если текущий день завершён — план начинается с `current_day + 1`.
- Новые задачи получают следующий свободный номер `T`.

### Diff

Система сравнивает новый план с текущим по ключам задач:

| Знак | Значит |
|---|---|
| `+` | Задача добавлена |
| `−` | Задача удалена (станет `cancelled`) |
| `~` | Изменились название, описание или критерии |
| `↪` | Задача перенесена в другой день или поменяла порядок |

Плюс изменения вех, `test_command` и числа дней. Diff показывается пользователю с кнопками «Утвердить» / «Правки» / «Отклонить».

### Применение утверждённого плана

В одной транзакции:

1. Текущая версия → `superseded`, новая → `approved`.
2. Задачи с новыми ключами создаются (`pending`), удалённые → `cancelled`, изменённые обновляются.
3. Обновляются вехи, `planned_days`, `test_command`.
4. Пересчитывается прогноз ([calendar.md](calendar.md#прогноз-окончания)).

После транзакции раннер (под блокировкой проекта) перегенерирует `PLAN.md` и коммитит в `dev`: `chore(plan): v3 — <change_summary>`. При создании проекта план v1 попадает в первый коммит.

## Разовые задачи

Задачи от `add_task` (ключи `A1`, `A2`, …) не входят в дни плана и не меняют `planned_days`. Выполняются в начале ближайшего запуска проекта (`when: next`) или сразу (`when: now`). Веху не имеют: попадают в `main` с ближайшим релизом.

## `PLAN.md`

Генерируется из БД целиком (агентам его редактировать запрещено — см. `AGENTS.md`). Пример:

```markdown
# План: todo-bot

> Сгенерировано Dayforge. Не редактировать вручную.
> Версия плана: 3 · Прогноз окончания: 28.10.2026 · День 4 из 10

**Telegram-бот для учёта расходов: FastAPI + aiogram + PostgreSQL**

Тесты: `uv run pytest -q`

## Вехи
- [x] M1 — Базовый бот (v0.1.0)
- [ ] M2 — Отчёты (v0.2.0)

## День 1 — Каркас проекта ✅
- [x] **T1** Каркас проекта
- [x] **T2** Подключение БД

## День 4 — Категории расходов ⏳
- [x] **T9** Модель категорий
- [ ] **T10** Команды /category ⏸ ждёт ответа

  Критерии: …

## Вне плана
- [x] **A1** Исправить опечатку в README
```

У невыполненных задач показываются описание и критерии, у выполненных — только название (подробности в `JOURNAL.md` и истории git).
